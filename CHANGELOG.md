## [1.0.0-rc.2] - 2026-10-27

Second release candidate of 1.0.0 (CONTRACT revision 6). The API can still change before 1.0.0.

### Added

- Regions: `PayriffRegion` (`.az`, the default, and `.sa`) and `PayriffConfig.region`, next to `environment`. Region `sa` (Saudi Arabia, GCC Pay) calls `https://api.gccpay.sa`. It has no sandbox: with `environment: .sandbox` card payments go to production and charge real cards, and `configure` logs a warning (with `enableLogging`). Every Client API call and the 3-D Secure callback check use the region's host; nothing else changes between regions.
- `PayriffConfig.apiBaseURL`: the API base URL of the configuration's region and environment. `PayriffConfig`'s `description`, `debugDescription` and mirror include the region, and so does the `Configured Payriff` log line.
- Example app: `PAYRIFF_REGION` (`az` or `sa`) next to `PAYRIFF_ENVIRONMENT` in `Example/Config/Example.xcconfig` and the `Secrets.example.xcconfig` template, passed to `PayriffConfig.region`.

### Removed

- `PayriffEnvironment.apiBaseURL`: the host now depends on the region too. Use `PayriffConfig.apiBaseURL`.

### Security

- Certificate pinning covers `api.gccpay.sa`, which serves a Google Trust Services chain (GTS Root R1, already pinned). GTS Root R4 is pinned as a backup for Google's ECDSA chains.
- Logs keep the path of `api.gccpay.sa` URLs, shortened like those of `api.payriff.com`; look-alike hosts still log as `scheme://host` only.

## [1.0.0-rc.1] - 2026-10-24

Release candidate of 1.0.0 for the security review. The API can still change before 1.0.0.


- First release.

### Added

- Card-only SDK (CONTRACT revision 5): your server creates the order with its secret key and hands the app `orderId` and `clientSecret`; the app pays it with the publishable key. The SDK never creates orders and never uses a secret key.
- `PayriffPaymentView` (UIKit) and `PayriffPaymentScreen` (SwiftUI): the ready-made card payment screen, like the card part of Payriff's hosted payment page (pay.payriff.com). It reads the order with `retrieveOrder` when it appears and shows the card form, a Pay button with the amount ("Pay 1.02 AZN"), the Mastercard and Visa badges, the secure line with a lock drawn in code, and a "Powered by Payriff" footer whose logo has a light wordmark in dark mode. Pay stays disabled while the order loads, while the form is incomplete and while paying, and when the order cannot be paid by card or did not load (a line under the button says why). Pay runs `confirmCardPayment` and passes the result of each attempt to `onResult`, which also gets a fatal error once; a failure that is not fatal keeps the order payable. The view pads the safe area, makes room for the keyboard and works as a page, in a bottom sheet and in a popup. A bottom sheet can be as tall as the view: `fittingHeight(forWidth:)` gives the height the view needs at a width, without the safe area, for a custom sheet detent; `onFittingHeightChange` (UIKit) and `PayriffPaymentScreen.onFittingHeightChange(_:)` (SwiftUI, for `.presentationDetents([.height(_:)])`) report it whenever it changes. The view still scrolls with the keyboard up.
- The payment view's line for an order that loaded but cannot be paid by card is localized (`view.notPayable`): "This order cannot be paid by card" in Azerbaijani, English and Russian.
- `PayriffPaymentViewStyle`: the background, the padding, the Pay button's colour, text style, height and corner radius, the secondary text colour, `showBadges`, `showSecureNote`, `showPoweredBy` and the card form's `formStyle`, and two texts: `payButtonLabel` replaces the word "Pay" (the amount and the currency still follow it) and `secureNoteText` replaces "Proceed securely by PCI DSS". The defaults reproduce the hosted payment page in light and dark mode.
- `Payriff.configure(_:)` with `PayriffConfig`: `publishableKey`, `environment` (production or sandbox), `language`, `enableLogging` and `allowCompromisedDevices`. `configure` never throws; a missing or invalid publishable key is logged as a warning and makes every later call fail with `INVALID_CONFIG`. Every call before `configure` fails with `NOT_CONFIGURED`.
- Native card form: `PayriffCardForm` (UIKit) and `PayriffCardFormView` (SwiftUI) with number, expiry, CVV and the cardholder name (shown by default, as on Payriff's hosted payment page; `showsHolder: false` hides it and the name is sent as `Unknown`); Visa and Mastercard with at most 16 digits; the brand's mark on a 36×24 white badge (a neutral outline before the brand is known, a 150 ms cross-fade, VoiceOver labels); validation and formatting exactly as Payriff.js; an upper-case cardholder name with the locale-independent mapping; light and dark mode, Dynamic Type and VoiceOver; Azerbaijani, English and Russian texts.
- `PayriffCardFormStyle` and `PayriffCardFormLayout`: by default the card form looks like the card form of Payriff's hosted payment page (`grouped`: "Card holder", then one "Card information" box with the number and the brand mark on top and expiry | CVC below, one error line per section, red outline on errors and Payriff's brand colour on focus, the hosted page's placeholders); every font, colour, size, spacing, title and the layout (`grouped` or `stacked`) can be changed with `PayriffCardForm(style:)`, `form.style` or `PayriffCardFormView(_:style:)`.
- Input security: numeric keyboards, no autocorrection or suggestions, AutoFill for number, expiry and name only, a masked CVV, no copy, cut or drag of the number and CVV, and values cleared after every result except a non-fatal failure.
- `Payriff.confirmCardPayment(_:orderId:clientSecret:from:)` (`async` and completion handler): loads the order (it must be payable by card), encrypts the card on the device (AES-256-GCM with fresh key material per attempt, the key wrapped with Payriff's pinned RSA-OAEP-SHA256 key), sends it once with an idempotency key, runs the next action (3-D Secure challenge or redirect in a sheet, the 3DS method in hidden web views, waits) and polls the status every 2.5 s for up to 120 s.
- `Payriff.retrieveOrder(orderId:clientSecret:)` returns a `PayriffClientOrder` (amount, currency, description, merchant name, status, language, payment methods, `isPayableByCard`).
- The Client API client: `X-Public-Key`, `X-Client-Secret` and `X-Client-App-Id` (the bundle id) on every request, never `Authorization`; redirects are never followed; 429 is retried after 1, 2 and 4 s and a network error on `/pay` once, with the same idempotency key and bytes; order ids are sent as one percent-encoded path segment; response bodies larger than 1 MB are never buffered.
- Certificate pinning (CONTRACT §16.15): every Client API call (order, pay, 3-D Secure step, status) to `api.payriff.com` and `sb-api.payriff.com` keeps iOS's TLS validation (chain, expiry, host name) and also requires a pinned Payriff CA key in the validated chain: the SubjectPublicKeyInfo SHA-256 of the current Sectigo intermediate and roots, or of a backup root of another major CA. A refused certificate is a `NETWORK_ERROR` that is not retryable ("Payriff's server certificate could not be verified."): nothing is sent and `/pay` is not retried. No setting turns pinning off. The 3-D Secure pages are not pinned.
- Device integrity (CONTRACT §16.16): card payments are refused on a jailbroken device (jailbreak files, a write outside the sandbox), when a hooking library such as Substrate, libhooker, ElleKit or Frida is loaded or a frida-server listens, and, in App Store and TestFlight builds, when a debugger is attached or `DYLD_INSERT_LIBRARIES` is set. The device is checked when the payment view appears, when `confirmCardPayment` starts and right before the card is encrypted; a refused payment fails with the new error code `DEVICE_COMPROMISED` and nothing is sent. The payment view then says "Card payments aren't available on this device for security reasons" (`view.deviceNotSupported`, in Azerbaijani, English and Russian), keeps Pay disabled, does not read the order and passes `DEVICE_COMPROMISED` to `onResult` once. `retrieveOrder` is never blocked, `Payriff.isDeviceCompromised` lets the app decide early, and nothing is checked on the simulator or on a Mac. `PayriffConfig.allowCompromisedDevices` (default `false`) lets payments run on jailbroken test devices during development and only logs a warning that names the signals. It works only in debug builds (the `DEBUG` condition the SDK is compiled with): any other build ignores it, refuses a compromised device as with `false` and logs a warning that the setting is ignored outside debug builds, so it can never reach production.
- The 3-D Secure sheet reads as part of the app: a page sheet with a grabber, the localized title only, a close button (Liquid Glass on iOS 26 and later, disabled while the status is checked), a native loader instead of a progress bar, bank pages inset 16 pt from the sides and 12 pt from the top and bottom on a white backdrop, no zoom, rubber-band scrolling, link previews or swipe navigation, and no injected JavaScript. Closing it asks for confirmation and checks the status once: a final status maps as usual, anything else is `pending(notFinal)`. The result is delivered exactly once, also when the host app dismisses the sheet or its scene is disconnected.
- The 3-D Secure close confirmation asks "Close this window?", says that the payment isn't finished and that its status will be checked, and offers "Close" and "Continue payment". Closing never cancels the order; the SDK checks its status once.
- Screen protection: opaque covers hide the card form and the 3-D Secure sheet while the app is inactive.
- 3-D Secure website data stays with the payment: the 3-D Secure sheet and the hidden 3-D Secure Method web views of one payment share one `WKWebsiteDataStore.nonPersistent()`, and every payment gets a new one. Nothing reaches the app's default website data store or the disk.
- `PayriffResult` (`success`, `declined`, `cancelled`, `pending`, `failed`) with `PayriffPayment` and `PayriffError` (stable codes, including `DEVICE_COMPROMISED`, `isFatal`, the invalid `fields` of `VALIDATION_FAILED`); results serialize to the JSON shared by every Payriff SDK (`Encodable` and `result.jsonObject`).
- `PayriffLogger.onLog` with `PayriffLogEntry.formatted`; no card data, keys, client secret, ciphertext or 3-D Secure values are ever logged, and unified-log lines are private in release builds. URLs, in every entry and in the bodies of the request and response details, never show their user info, query or fragment; only Payriff's API hosts show the path, with every segment of 16 or more characters shortened to its first and last 4 (`/api/v3/client/orders/7c9e…0ae7/pay`), any other host (bank and 3-D Secure pages) shows as `scheme://host[:port]`, and other schemes as `<scheme>:…`. Debug builds also log every API request and response as redacted, pretty-printed JSON; release builds never do.
- A README section "Fulfil on your server", a privacy manifest, Swift Package Manager support and a podspec (the pod is not on CocoaPods trunk yet).
- Example app: one screen with an "Order from your backend" section (orderId and clientSecret fields, and Paste for the `{"orderId", "clientSecret"}` JSON your server returns or the two values separated by white space), and Pay in page, Pay in bottom sheet and Pay in popup, which show `PayriffPaymentScreen` in each container (the bottom sheet is as tall as the view); the outcome opens in a result sheet. Debug builds write the SDK log to `Documents/payriff-sdk.log`. The example holds no secret key and never creates orders.
